Diagnostics

1 Why to run diagnostics before analysis?

Running an analysis on a poorly specified cohort is worse than running no analysis at all! It can produce numbers that look credible but are wrong. Diagnostic tools exist to systematically surface problems with your phenotype algorithms and cohort logic before you commit to an analytical result.

In the OHDSI ecosystem, the diagnostic workflow centres on two tools: CohortDiagnostics and PhenotypeR. We will introduce PhenotypeR in this tutorial.

3 Setup

In this example, we better work with the Eunomia dataset as an example instead of the omock data, because the number and variety of drug exposures available in the synthetic data are more broad in the Eunomia dataset. You can also download example datasets from the omock package, like the GiBleed dataset. The documentation of the package is here.

Code 
library(CohortConstructor)
library(CodelistGenerator)
library(CDMConnector)
library(omopgenerics)
library(omock)
library(dplyr)
library(duckdb)


requireEunomia()
db <- DBI::dbConnect(duckdb::duckdb(), dbdir = eunomiaDir())
cdm <- cdmFromCon(db, 
                  cdmSchema = "main", 
                  writeSchema = "main", 
                  writePrefix = "greg_")


semaglutide <- getDrugIngredientCodes(cdm = cdm,
                                      name = "semaglutide")

t2dm <- getCandidateCodes(
  cdm = cdm,
  domains = "Condition",
  includeDescendants = TRUE, 
  includeAncestor = FALSE,
  keywords = c("type 2 diabetis mellitus", "T2DM")
)

acute_pancreatitis <- getCandidateCodes(
  cdm = cdm,
  domains = "Condition", 
  includeDescendants = FALSE,
  includeAncestor = FALSE,
  keywords = c("Acute pancreatitis")
)

# Build drug exposure cohorts (one per GLP-1 agent)
cdm$semaglutide_cohort <- conceptCohort(
  cdm         = cdm,
  conceptSet  = semaglutide,
  name        = "semaglutide_cohort",   # name of the cohort table in the CDM
  exit = "event_end_date",
  overlap = "merge")


# Build condition cohorts
cdm$t2dm_cohort <- conceptCohort(
  cdm         = cdm,
  conceptSet  = t2dm,
  name        = "t2dm_cohort"
)

cdm$ap_cohort <- conceptCohort(
  cdm         = cdm,
  conceptSet  = acute_pancreatitis,
  name        = "ap_cohort"
)

cdm <- bind(cdm$semaglutide_cohort, cdm$t2dm_cohort, cdm$ap_cohort, name = "study_cohorts")

4 Example pipeline

In this tutorial we will provide an example on how to run diagnostics with PhenotypeR, but further documentation can be found in the package documentation, with all available functions in its reference index and in this other tutorial.

We will see the results in a Shiny App, please, make sure that you have the necessary resources to run a shiny app in R.

4.1 1. Running PhenotypeR

Code 
library(PhenotypeR)
library(here)
library(shiny)

# A folder on the local file system to store results
outputDir <- here::here("Results")

# Study parameters -----------------------------------------------------
MinCellCount <- 5 # Less than 5 counts because small numbers are a danger to privacy
if (!dir.exists(outputDir)) {
  dir.create(outputDir)
}
createLogger(outputDir, dbName)
log("Starting diagnostics")

log("Creating phenotype cohort")

cdm <- bind(cdm$semaglutide, cdm$ap_cohort, cdm$t2dm_cohort, name = "all_cohorts")

# Run phenotypeR -------------------------------------------------------
log("Running PhenotypeR")

phen_all_cohorts <- phenotypeDiagnostics(
  cdm$all_cohorts_table,
  diagnostics = c(
    "databaseDiagnostics",
    "codelistDiagnostics",
    "cohortDiagnostics",
    "populationDiagnostics"
  ),
  survival = TRUE,
  cohortSample = 7000, # You can adapt these numbers as you wish and depending
  matchedSample = 3000, # on your sample size
  populationSample = 1e+05
)

# Export all the results -----------------------------------------
log("Exporting results")

PhenotypeR::exportSummarisedResult(
  phen_all_cohorts,
  fileName = paste0("phenotypeR_results_{cdm_name}_{date}.csv"),
  path = outputDir,
  minCellCount = MinCellCount
)

log("Finishing diagnostics zipping results")

zip(
  zipfile = here(outputDir, paste0("phenotypeResults-", dbName, ".zip")),
  files = list.files(outputDir),
  root = outputDir
)

# To see your results in a Shiny App -----------------------
results <- omopgenerics::importSummarisedResult(
  path = here("Results"),
  # folder containing your CSV
)

PhenotypeR::shinyDiagnostics(results, directory = "Results")
Tip

When the Shiny project opens, you can run the command shiny::runApp() and the app will open on your R browser!

4.2 2. Interpreting the results

4.2.1 Cohort counts and attrition

The first diagnostic is always: how many patients are in the cohort, and how many were lost at each step?

Our study: A well-specified attrition table for the semaglutide cohort might look like this:

Step Remaining N
Initial drug exposure records 45,210
First entry per person 12,847
≥ 365 days prior observation 11,203
No prior GLP-1 RA (washout) 9,841
T2DM diagnosis before index 8,654
Age ≥ 18 8,640
Index date 2023–2024 6,112

If the washout step removes more than 60% of patients, we need to think whether this makes sense. It may indicate that your concept set is too broad and is capturing repeat prescriptions of the same episode, or that the database has many prevalent users.

Quick check: Your attrition table shows 10,000 patients after requireIsFirstEntry() but only 200 after requirePriorDrugWashout(days = 365). What does this most likely indicate?

When the vast majority of patients are excluded by the washout criterion, it means most patients who appear in the database with this drug already had prior exposure, i.e., they are prevalent users. This is common for drugs that have been on the market for many years. The new-user design deliberately excludes these patients to avoid prevalent-user bias, but it does reduce your study population substantially. This is a design trade-off, not a bug.

Important

Additionally, we need to consider the fact that we usually can only recover drug prescriptions, not the fact that the subjects in our cohort are actually taking the drug. This is constraining, and we need to bear in mind when setting a washout period the usual time between prescriptions.

4.2.2 Codelist diagnostics

The cohort code use can help us see whether relevant codes have been introduced or whether there are substances that we are including that we might want to avoid. At the same time, the orphan codes tag allows us to see potentially missed concepts that might be relevant for our study.

Caution

For the semaglutide exposure cohort, you expect to see Ozempic (injectable) and Rybelsus (oral) as the most used concepts. If you see unexpected concepts (which you should not because you have reviewed the list with a pharmacist, right?) your concept set needs revision.

4.2.3 Baseline and large-scale characteristics

When seeing the baseline characteristics and large-scale characteristics of your cohorts, you will be able to see whether the patients included in each cohort differ substantially between them. In our study, for example, we might see that patients receiving semaglutide and tirzepatide differ substantially. When doing the comparisons between GLP-1 RA for the safety part of our study, we need to take this into account, as it is the core confounder that we can have in our study “Are the five GLP-1 RA cohorts comparable at baseline, or do they differ systematically in ways that could explain any observed difference in pancreatitis risk?”

Large-scale characteristics are also nice because you can see the top concepts of conditions, drugs, measurements and all other domains recorded for your cohorts. If you are making a just-males cohort and you see that one of your top concepts is pregnancy, there might be something wrong with your cohort definition. You might also identify comorbidities, comedication or previous conditions that might affect the risk of your outcome of interest.

Tip

Watch out for large-scale characteristics, you might identify potential confounders!

4.2.4 Cohort overlap

High overlap between exposure cohorts when you do not expect that could mean that your cohort exit criteria are not correctly excluding patients who switch between agents. For example, if a patient switches from liraglutide to semaglutide, they should exit the liraglutide cohort at the switch date and enter the semaglutide cohort. Failure to handle this correctly leads to immortal time and misclassification bias.
